# Data Model: Locked Backend Setup and Starting Schema

This feature stores two recorded artifacts in the repo and one application
table in PostgreSQL. It does not store calls, templates, scores, or agents.

## Dependency record

Not a database table. It is `backend/uv.lock`, produced from
`backend/pyproject.toml`.

| Field | Rule |
| --- | --- |
| Declared dependencies | Runtime: the packages the API already needs (FastAPI, uvicorn, SQLAlchemy, psycopg), plus Alembic and a build backend so `uv run serve` exists. Dev: pytest. |
| Locked versions | Exact versions and hashes for one revision. |
| Identity | One lock for developers and for the running app. |

Validation:

- Install fails if `uv.lock` is absent.
- Install with `--frozen` fails if `pyproject.toml` and `uv.lock` disagree.
- Two installs of the same revision resolve the same versions.

The frontend package list is unchanged and is not part of this record.

## Schema revision

Alembic's version table, created by Alembic itself when the first revision
is applied. The project stores the revision file under
`backend/alembic/versions/`.

| Field | Rule |
| --- | --- |
| Revision id | One ordered id. This feature has a single revision, the head. |
| Down revision | Empty. This is the first revision. |
| Effect | Creates `app_meta`. Does not drop an existing table. |

State:

1. Empty database. No application tables. No version row.
2. `uv run migrate` succeeds. Version row points at this revision.
   `app_meta` exists.
3. `uv run migrate` again. Version row and `app_meta` stay as they are.
   The command exits successfully.

A database that already has an `app_meta` table whose columns do not match
this model is a conflict. The command stops and leaves existing rows in
place.

## Starting schema: `app_meta`

The initial application table. Created only by the first Alembic revision.
Clean Architecture splits this into a domain entity and a persistence
mapping.

### Domain entity (`app/domain/app_meta.py`)

Pure type. No SQLAlchemy, FastAPI, or Alembic imports.

| Field | Rules |
| --- | --- |
| `id` | Optional until persisted. Identity is assigned by the database. |
| `key` | Required non-empty text. Unique among entities of this type. |
| `value` | Required non-empty text. |

Validation lives on the entity (or a domain factory). A missing `key` or
`value` is rejected before any adapter runs. Uniqueness across rows is a
domain rule enforced when persisting through an adapter.

### Persistence mapping (`app/adapters/persistence/models.py`)

SQLAlchemy table mapping that mirrors the entity for PostgreSQL.

| Column | Type | Rules |
| --- | --- | --- |
| `id` | integer | Primary key. Generated by the database. |
| `key` | text | Required. Unique. |
| `value` | text | Required. |

Relationships: none. No foreign keys.

Validation:

- A row without `key` or `value` is rejected.
- Two rows with the same `key` are rejected.
- The table may contain zero rows after the migration. This feature does
  not seed coaching data or require a starting row.

The health check does not read `app_meta`. The `CheckHealth` use case
only asks a `DatabaseProbe` whether the database accepts a connection.
Presence of the table is checked by the migration command and by the
offline SQL test.

## Out of this model

- Calls, task templates, step results, scores, and agents.
- Any change to the screen's data.
- A second dependency list.
